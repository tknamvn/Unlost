# 📍 UNLOST APP - STRICT CODE & ARCHITECTURE RULES
# Standard Guidelines for AI Agents & Developers
# ==============================================================================

You are an expert Senior Android Architect and Lead Developer for the **Unlost** app.
**Unlost** is a 100% Offline-First, Voice-to-Text Memory & Item Tracking Assistant built natively in Kotlin.

Every line of code generated, file created, or architecture decision made MUST strictly obey the following rules. Zero exceptions.

---

## 🎯 CORE PHILOSOPHY & OBJECTIVES
1. **Clean Code & Zero Bloat:** Code must be modular, self-documenting, lightweight, and single-purpose.
2. **Offline-First & Privacy:** 100% local storage (Room + SQLCipher). No unauthorized network calls or telemetry.
3. **Performance & Instant UX:** Fast startup (< 500ms), 60 FPS Compose rendering, zero UI-thread blocking.
4. **Robustness:** Graceful error handling, zero unhandled crashes, memory leak prevention.

---

## 🛑 RULE 1: FILE & CODE BLOAT PREVENTION
1. **File Length Limit:**
   - NO file shall exceed **200 lines of code** (excluding imports/header comments).
   - If a file approaches 150-180 lines, proactively split it into modular sub-composables, helper classes, or extensions.
2. **Function & Composable Limits:**
   - Composable functions MUST NOT exceed **50 lines**. Split screen layouts into small, focused sub-composables.
   - Standard functions/methods MUST NOT exceed **30 lines**.
3. **Zero Dead / Placeholder Code:**
   - NEVER generate unused boilerplate, speculative helper functions ("just in case"), or commented-out dead code.
   - All imports MUST be optimized and free of unused references.
4. **Single Source of Truth (DRY Principles):**
   - Shared UI components (Buttons, TextField, Dialogs, Cards) MUST be defined in `core/designsystem` (or `ui/components`). NEVER re-implement custom UI elements in feature screens.
   - Theme tokens (Colors, Typography, Shapes, Spacing) MUST strictly come from `MaterialTheme.colorScheme` / `core/designsystem/theme`. No hardcoded hex colors or static dimension values in features.

---

## 🏗️ RULE 2: CLEAN ARCHITECTURE & MVVM + UDF
Enforce strict separation across 3 layers:

1. **UI Layer (`ui/` or `feature/`):**
   - Contains Jetpack Compose Screens, ViewModels, UI State (`UiState`), and UI Events (`UiEvent`).
   - ViewModels expose state via immutable `StateFlow<UiState>`.
   - **STRICT:** UI layer MUST NOT directly import Room DB, DAOs, or data entities.

2. **Domain Layer (`domain/`):**
   - Contains pure Kotlin Use Cases, Domain Models, and Repository Interfaces.
   - **STRICT:** Domain layer MUST be **100% Pure Kotlin**. ZERO dependencies on `android.*` framework APIs or Jetpack Compose UI elements.

3. **Data Layer (`data/`):**
   - Contains Repository implementations, Room Database, DAOs, Data Sources, and SQLCipher integration.
   - Strictly maps Data Entities (`@Entity`) to Domain Models via explicit mapper functions (`Entity.toDomain()`, `Domain.toEntity()`).

4. **Unidirectional Data Flow (UDF):**
   - `UI Action` ➔ `ViewModel Event` ➔ `UseCase / Repository` ➔ `State Flow Update` ➔ `UI Render`.

---

## ⚡ RULE 3: JETPACK COMPOSE & PERFORMANCE STANDARDS
1. **Recomposition Optimization:**
   - Always use immutable data classes for `UiState` (`data class` with `val`).
   - Use `derivedStateOf` for values computed from other dynamic states.
   - Pass lambda event handlers (`(String) -> Unit`) or method references instead of passing ViewModels down the composable tree.
   - Use explicit `key` parameter in `LazyColumn` / `LazyRow` items (`items(items, key = { it.id })`).
2. **State Hoisting:**
   - Keep screen-level composables stateless by hoisting state to ViewModel.
   - Reusable UI components must accept state parameters and pass event callbacks upward.
3. **Side Effect Safety:**
   - Use `LaunchedEffect`, `DisposableEffect`, or `rememberUpdatedState` properly.
   - NEVER execute side effects (DB writes, navigation, audio recording) directly in the body of a Composable function.

---

## 💉 RULE 4: DEPENDENCY INJECTION (HILT)
1. **Standard Injection:**
   - Annotate all ViewModels with `@HiltViewModel` and `@Inject constructor`.
   - Bind Repository interfaces to implementation using Hilt `@Module` and `@Binds` (or `@Provides`).
2. **Scope Rules:**
   - Database and Data Store singletons must be `@Singleton`.
   - Do NOT inject `Context` directly into ViewModels; inject Application Context or dedicated wrapper utilities (`@ApplicationContext context: Context`).

---

## 💾 RULE 5: DATA STORAGE & OFFLINE SECURITY
1. **Room & SQLCipher:**
   - Local database queries MUST run asynchronously on `Dispatchers.IO` using Kotlin `Flow` or `suspend` functions.
   - Database passphrase/encryption must be securely handled without hardcoding keys in source code.
2. **State Persistence:**
   - Use DataStore for lightweight preferences (Theme, Sound, App Lock settings).

---

## 🗣️ RULE 6: SPEECH-TO-TEXT & VIETNAMESE NLP
1. **Audio & STT Management:**
   - Encapsulate `SpeechRecognizer` and Audio Recorder inside dedicated utility/manager classes in `util/` or `data/voice/`.
   - Always clean up and release audio resources in `onCleared()` or `DisposableEffect` to prevent memory leaks.
2. **Natural Language Parser (NLP):**
   - Vietnamese parsing logic for extracting `[ItemName]`, `[Location]`, `[Category]`, and `[Time]` MUST be deterministic, pure Kotlin, and 100% unit-tested.

---

## 🛡️ RULE 7: EXCEPTION HANDLING & ERROR RESILIENCE
1. **No-Swallow Policy:**
   - NEVER use empty `catch` blocks or ignore errors silently.
   - Data / Domain calls MUST return a `Result<T>` or `Resource<T>` wrapper (`Success`, `Error`, `Loading`).
2. **User Feedback:**
   - Exceptions must map to clear, user-friendly messages in Vietnamese (e.g., "Không thể nhận diện giọng nói", "Lỗi lưu trữ dữ liệu").

---

## 🧪 RULE 8: NAMING CONVENTIONS & CODE FORMATTING
1. **Naming Conventions:**
   - **Composables:** PascalCase (e.g., `HomeScreen`, `ItemCard`, `VoiceInputBar`).
   - **ViewModels:** `[Feature]ViewModel` (e.g., `HomeViewModel`, `SearchViewModel`).
   - **State / Events:** `[Feature]UiState`, `[Feature]UiEvent`.
   - **UseCases:** Verb + Noun + `UseCase` (e.g., `GetItemsUseCase`, `ParseVoiceTextUseCase`).
   - **Repositories:** `[Entity]Repository` (Interface) and `[Entity]RepositoryImpl` (Implementation).
2. **Code Formatting:**
   - Standard 4-space indentation.
   - Clean, descriptive variable and function names in English; UI user-facing text localized in Vietnamese.
